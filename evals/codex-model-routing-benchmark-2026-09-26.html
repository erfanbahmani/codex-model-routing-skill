Evidence-led benchmark analysis / 26 September 2026

Codex Model Routing
Tokens, credits & correctness

A presentation-ready analysis of two controlled test campaigns across small edits, extraction, configuration, feature work, a graph bug, code review, and scheduling.

Scope: current routing-policy source at commit d846c8b · Codex CLI 0.156.1

What this skill does. Codex Model Routing is a written decision policy for a strong lead model. The lead scopes the task, chooses direct work or one bounded lower-model worker, verifies the worker’s actual model, reviews the result, and counts tokens across the entire agent tree. It does not automatically switch the active lead model or guarantee savings.

01 / Executive readout

What the evidence actually says

Natural routing with an Astra lead: 11 matched pairs (22 completed runs) used 2,841,526 tokens without the skill and 2,813,604 with it. All predeclared checks passed. Repricing each recorded model’s input, cached input, and output at the current Codex Standard rate card gives 218.604 versus 109.182 credits. That is a test-mix result, not a proven general saving or an observed bill.

Direct work vs delegation: the seven direct-route treatment runs saved 671,952 tokens; the four Luna-delegated treatment runs added 644,030 tokens. Both repetitions of the graph bug and scheduler used more tokens with delegation. Cheaper worker tokens outweighed that token growth in the rate-card calculation, but only because models have very different prices.

Forced Sol/Astra manager comparison: on two implementation tasks repeated twice, Sol→Luna used 148.3% more tokens than Sol direct, while its estimated credits were 22.3% lower. Both Sol→Luna bug outputs failed a later, uniformly applied missing-root check that both Sol-direct outputs passed. Therefore the lower credit figure is not evidence of lower cost for an equally correct bug fix.

Decision this benchmark can support

Use the skill as a selective routing policy to investigate, not a blanket token-reduction promise. In the observed natural-routing mix, the model-weighted credit estimate fell substantially; total tokens barely changed. The strongest safe operational lesson is to keep short work direct and require a quality gate before treating delegated work as a cheaper equivalent.

Why two campaigns are separate

Campaign A measures the skill’s own route selection with an Astra/ultra lead; the control was free to use normal agents and did so. Campaign B forced a Luna worker in two complex tasks to compare manager strategies; it is not a test of the current policy’s natural route choice. Totals, percentages, and quality claims are compared within each campaign only.

Method follows benchmark-reporting guidance that requires decision fit, workload provenance, task-specific quality checks, complete accounting, and explicit limits [1–4]. Earlier 21 September tests used an older policy and are excluded from current-policy aggregates.

02 / Protocol and accounting

How the benchmark was measured

Campaign A · natural route

Seven synthetic task types, 11 matched pairs, fresh disposable workspace and lead session per run. Same task, starting fixture, lead gpt-6-astra/ultra, and acceptance check within each pair. Only treatment received the unchanged skill text in its prompt. Controls could delegate normally; they created 13 Astra/ultra descendants. Treatment chose seven direct runs and four runs with exactly one runtime-confirmed Luna/medium worker. The skill was not installed.

Campaign B · forced manager strategy

Two implementation tasks × three strategies × two fresh runs: Sol direct, Sol→Luna, Astra→Luna. The managed arms received the skill plus an explicit requirement to use one worker; direct Sol had no skill and no delegation. Runtime model/effort and full thread tree were checked. All 12 passed predeclared checks; a later bug edge case is reported separately.

Both campaigns used isolated synthetic fixtures, ignored user configuration, disabled installed-skill and plugin discovery, and supplied the same runtime model metadata mechanism to comparison arms. No production project or personal skill directory was modified.

Metrics and price basis

Processed tokens = input + output across the lead and every descendant, with each thread counted once. Cached input is a subset of input; reasoning output is a subset of output. Estimated Codex credits = Σ by model of [(input − cached input) × input rate + cached input × cached rate + output × output rate] / 1,000,000. Recorded cache-write tokens were zero. Rates below are the Codex Standard-speed rate card viewed 26 September 2026 [5].

04 / Campaign A · interpretation

Where the gain came from—and where it did not

Small and bounded tasks: the skill kept seven treatment runs direct, while the unrestricted controls created Astra children. Those seven pairs saved 671,952 processed tokens in total. The task-level checks covered exact Decimal formatting, document extraction, 12-file configuration, feature API behavior, and a seven-criterion refund review. This indicates a useful direct-work bias against this agent-prone control; an already-direct baseline may show less benefit.

Substantial implementation: Luna was actually used in the two graph-bug and two scheduler treatments. Each of those four runs used more tokens than its match; together they added 644,030 tokens and nearly erased the direct-run gains. The graph-bug treatment totals were 535,590 and 535,307 versus 416,509 and 365,534. Scheduler treatments were 604,222 and 580,912 versus 451,801 and 378,157.

In the first graph-bug pair, the Astra lead used 214,039 tokens with the skill vs 217,164 in control—a saving of only 3,125. The Luna worker used 321,551 tokens, while all control workers combined used 199,345. The extra worker work more than explains the token regression. Observable traces include repeated reading, diff inspection, a follow-up, corrections, and rerun checks; they do not prove a universal model tendency.

Why credits still fell: the Codex Standard rate card assigns Luna 1/100 of Astra’s input, cached-input, and output credits per token. In the delegated task categories, many more low-rate Luna tokens replaced higher-rate Astra activity. The four Luna threads together contributed about 1.439m tokens but only 0.956 modeled credits; the two delegated categories’ Astra leads still contributed 56.803 credits. This is price substitution, not token efficiency.

Quality coverage matters

All 22 Campaign A outputs passed its independent predeclared checks and the applicable fixture suites. That does not establish complete semantic equivalence: Campaign B later exposed a missing-root bug case absent from its original acceptance checks. Campaign A’s graph check covered a missing intermediate row, not the later missing root case. The two campaigns use different fixtures and should not be conflated.

Observable routing, not an installed product

All Campaign A leads were runtime-confirmed Astra/ultra. All four treatment workers were explicitly pinned and runtime-confirmed Luna/medium, with no nested workers. The test supplied SKILL.md verbatim in treatment prompts and deliberately left personal skill directories untouched. It verifies the policy when provided, not automatic discovery in every Codex or Zed client. The Terra route did not trigger.

06 / Quality, limits, decision

A cheap run is useful only if it is correct

The predeclared bug checks covered unique descendants, duplicate edges, cycles, unrelated threads, NULL usage, and traversal through a missing intermediate row. After read-only review, one additional check tested a root ID with no thread row but an edge to a known child. The root should appear as unknown, the child should remain visible with known tokens, and the total should be incomplete. Both Sol-direct outputs passed; both Sol→Luna and one Astra→Luna output exited “Thread not found.” No trial was repaired or excluded after this finding.

The extra check is post hoc, so it is not a substitute for a predeclared pass rate. It is nonetheless direct evidence that the planned suite missed a meaningful edge case. A claim that Sol→Luna delivered the same bug-fix quality for fewer credits is unsupported. We do not report a cost-per-correct-result estimate for that arm.

Threats to validity

  • Small and selected: one or two repetitions per category, synthetic fixtures, and no production-workload sampling. Do not infer statistical significance or a team-wide savings rate.
  • Control choice: Campaign A’s no-skill controls all spawned Astra agents; an already-direct control could erase much of the observed benefit.
  • Different treatment: Campaign B forced delegation and omitted the skill from direct Sol. It tests those procedures, not a pure isolated policy effect.
  • Cost model: credits were recomputed from telemetry at a later rate card; actual subscription charges, quota debits, context-tier adjustments, and any contractual discounts were not measured.
  • Runtime conditions: some sessions reconnected, and the forced-strategy fixtures lacked Git history. No clean latency comparison exists.
  • Coverage: quality gates were task-specific but incomplete, as the later root case demonstrated. Current repo implementation is not implicated by the fixture failures.

What is safe to say in a presentation

“In an 11-pair synthetic retest, this routing policy was actually followed and reduced estimated Standard-speed model credits by 50.1% for that task mix, while processed tokens were nearly unchanged. A separate forced-delegation test showed more tokens and uncovered a correctness edge case, so general cost or quality superiority is not established.”

Next defensible test: pre-register all quality cases (including missing root), sample real Git-backed team tasks, include direct Sol and direct Astra baselines, run more repetitions in randomized order, retain request-level usage and actual credit-dashboard data, and report cost only for outputs meeting the same acceptance gate. No new trials were run for this document.
